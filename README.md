# PricePulse

Микросервисная платформа мониторинга и анализа цен в интернет-магазинах и маркетплейсах.

Пользователь добавляет товар, система собирает предложения, сохраняет историю цен и подбирает варианты по цене, наличию, доставке и качеству продавца.

## Текущее состояние

Репозиторий содержит минимальный Maven-проект с целевой версией Java 25. Сервисы, инфраструктура и тесты пока не реализованы. Ниже описана целевая архитектура и порядок разработки, а не готовые возможности.

## Первый рабочий сценарий

1. Пользователь добавляет отслеживаемый товар по ссылке магазина.
2. Система создаёт задание на сбор предложений.
3. Collector параллельно опрашивает два демонстрационных адаптера магазинов.
4. Результаты поступают через Kafka в сервис мониторинга.
5. Сервис сохраняет предложения и наблюдения цен в PostgreSQL.
6. REST API возвращает актуальные предложения и историю цены.

Демонстрационные адаптеры должны воспроизводимо моделировать изменение цен, задержки, отсутствие товара и ошибки. Подключение реальных источников — следующий отдельный этап.

## Границы сервисов

| Сервис | Ответственность | Данные |
| --- | --- | --- |
| Monitoring | Отслеживаемые товары, задания сбора, предложения, история цен, пользовательские ограничения | Собственная база PostgreSQL |
| Collector | Адаптеры магазинов, параллельный сбор, нормализация результатов, ограничения запросов | На первом этапе без собственной бизнес-БД |
| Notification | Правила уведомлений, обработка изменений, учёт попыток доставки | Собственная база PostgreSQL; добавляется позже |

На первом этапе запускаются Monitoring и Collector. Ранжирование и анализ скидок начинаются как модули Monitoring; выделение отдельного Analytics-сервиса требует причины: независимого масштабирования, иной модели хранения или отдельного цикла разработки.

Один экземпляр PostgreSQL в локальном Docker Compose может обслуживать отдельные базы сервисов. Сервисы не читают чужие таблицы. API Gateway и отдельный сервис идентификации не входят в первый этап; до внешнего доступа необходимы аутентификация и проверки владения отслеживаемыми товарами.

## Модель данных

- `TrackedProduct`: объект мониторинга с владельцем и ссылкой на исходный товар.
- `StoreListing`: карточка товара в конкретном магазине, связанная с отслеживаемым товаром.
- `Offer`: предложение конкретного продавца — цена, валюта, наличие, доставка, рейтинг и время наблюдения.
- `PriceObservation`: неизменяемое наблюдение цены для предложения.
- `CollectionJob`: задание сбора и его состояние по источникам.

В первой версии связи карточек разных магазинов задаются явно. Автоматическое сопоставление товаров — отдельная бизнес-задача: нужно учитывать модель, вариант, комплектацию и регион. Предложения нельзя объединять только по похожему названию.

Деньги хранятся в `BigDecimal`/`NUMERIC` с валютой. Неизвестные наличие, стоимость доставки и срок доставки сохраняются как неизвестные значения. Сбор хранит как время наблюдения, так и время получения результата.

## Асинхронный поток

`REST → Monitoring → CollectionRequested → Collector → OfferObserved / CollectionSourceFinished → Monitoring`

- Monitoring сохраняет задание и событие в outbox в одной транзакции PostgreSQL.
- Издатель outbox отправляет события в Kafka. Повторная отправка допустима.
- Collector обрабатывает запрос и публикует отдельные наблюдения и итог каждого источника, включая ошибки и пустые результаты.
- Monitoring сохраняет идентификатор обработанного события и бизнес-изменения в одной транзакции. Подтверждение Kafka выполняется после её завершения.
- Для зависших заданий предусмотрены deadline и сверка незавершённых источников. Успех одного источника не скрывает ошибку другого.

Конверт события содержит `eventId`, `eventType`, `schemaVersion`, `occurredAt`, `correlationId`, `jobId` и `trackedProductId`. Ключ партиции — `trackedProductId`. Порядок Kafka в партиции не заменяет проверку времени наблюдения: старый результат сохраняется в историю, но не должен перезаписывать более свежую текущую цену.

Базовая гарантия — доставка как минимум один раз с идемпотентной обработкой. Уникальное ограничение на `eventId` предотвращает повторное применение одного события; идентификатор наблюдения должен оставаться стабильным при повторной публикации. Outbox не гарантирует отсутствие дублей.

## Конкурентность и отказоустойчивость

- Virtual Threads используются для блокирующего I/O адаптеров; число одновременных запросов ограничивается глобально и для каждого магазина.
- `CompletableFuture` применяется там, где нужна композиция независимых результатов. Все задачи получают явный executor, таймаут и контролируемое завершение.
- Таймауты соединения и чтения задаются на HTTP-клиенте. Истечение таймаута future само по себе не гарантирует остановку сетевого запроса.
- Повторы ограничены, используют backoff с jitter и учитывают тип ошибки. Для окончательных ошибок предусмотрены dead-letter topic и управляемый повторный запуск.
- Вызовы магазинов не выполняются внутри транзакций PostgreSQL.
- Kafka listener не подтверждает задание после простой передачи работы в фоновый поток. Первый вариант завершает ограниченный по времени сбор и публикацию результатов до подтверждения; повторная доставка может повторить запросы к источникам.
- Конкурентные обновления актуального предложения защищены проверкой времени наблюдения и оптимистической блокировкой либо условным обновлением в БД.

Redis вводится после появления измеримой задачи: кеш актуальных предложений и распределённое ограничение частоты обращений. PostgreSQL остаётся источником истины. Потеря кеша не должна приводить к потере истории; поведение при недоступности ограничителя запросов задаётся явно.

## Бизнес-логика следующих этапов

Сначала предложения проходят жёсткие фильтры пользователя, затем ранжируются. Базовая стоимость — цена товара плюс известная доставка в одной валюте. Неизвестная доставка явно обозначается. Скоринг учитывает стоимость, срок доставки, рейтинг продавца и свежесть данных; API возвращает объяснение результата.

Анализ скидок сравнивает текущую цену с историей сопоставимого предложения за заданное окно, например 30 дней. Медиана и минимум помогают оценивать изменение цены; процент скидки магазина сохраняется отдельно от расчёта по наблюдениям. При недостаточной истории система сообщает об этом.

Уведомления создаются при переходе к подходящему состоянию или достижении нового порога, а не после каждого сбора. Для защиты от повторов нужны идентификатор уведомления, журнал доставки и политика повторных попыток. Гарантия однократной внешней доставки зависит от поддержки идемпотентности каналом уведомлений.

## План разработки

| Этап | Результат | Критерий готовности |
| --- | --- | --- |
| 1. Основа | Maven-модули Monitoring и Collector, PostgreSQL, Kafka, миграции, Docker Compose | Сервисы запускаются, health checks работают, миграции применяются |
| 2. Сквозной сбор | REST, два демонстрационных адаптера, события, предложения и история | Добавленный товар получает результаты; ошибка одного источника не теряет успешный результат другого |
| 3. Надёжность | Outbox, дедупликация, deadline, повторы, dead-letter topic | Повтор события, перезапуск потребителя и запоздалый результат не искажают данные |
| 4. Подбор предложений | Фильтры, объяснимое ранжирование, анализ скидок | Проверены неизвестная доставка, разные валюты, устаревшие данные и недостаточная история |
| 5. Redis и нагрузка | Кеш, лимиты запросов, измерение конкурентности | Измерены пропускная способность и p95; проверена деградация при отказе Redis |
| 6. Уведомления | Notification, правила, журнал доставки | Повторные события не создают повторную бизнес-команду на уведомление |
| 7. Реальные источники и эксплуатация | Первый реальный адаптер, CI/CD, Prometheus, Grafana | Контролируются ошибки источников, lag Kafka, возраст outbox и свежесть предложений |

## Проверки

JUnit и Mockito используются для бизнес-правил и адаптеров. Совместимую с выбранным Spring Boot версию JUnit нужно проверить при настройке зависимостей; требование JUnit 5 при необходимости закрепляется явно.

Testcontainers проверяет реальные PostgreSQL, Kafka и позже Redis. Ключевые интеграционные сценарии: повтор события, сбой между записью outbox и публикацией, сбой после commit до подтверждения Kafka, конкурентные обновления и частичный отказ источников.

Первый инженерный шаг — реализовать этапы 1–2 как небольшой работающий вертикальный срез. Точные версии Spring Boot 4.x и инфраструктуры фиксируются при реализации после проверки совместимости с Java 25.
